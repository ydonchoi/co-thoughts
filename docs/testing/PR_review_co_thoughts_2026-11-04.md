# co-thoughts 평가 / PR 리뷰 — 2026-11-04

## 판정

**평가: 유망한 프로토콜 + 안전 경계 참조 구현. 현 상태를 완성된 v2.0 런타임 또는 실증 검증된 방법론으로 승인하기는 어렵다.**

**PR 권고: Request changes (범위와 릴리스 기준을 명확히 한 뒤 재검토).**

이번 검토는 저장소의 README, 활성 프로토콜, 런타임 핵심 모듈, 평가 코드 및 T54/T55 문서를 읽은 정적 검토다. 테스트를 실행하지 않았으며, 실제 LLM 제공자, 외부 도구, Notion 영속 저장을 실행해 확인하지 않았다.

## 강점

- **인식론적 경계가 일관된 설계 목표다.** 인간의 최종 판단, 동의와 증거의 분리, AI 출력의 기본 UNVERIFIED 처리, 검증 상태와 저장 상태 분리를 핵심 규칙으로 반복해서 명시한다.
- **런타임 경계는 일부 구체화돼 있다.** `SafetyPolicy`는 도구 실행과 외부 부작용을 기본 거부하며 작업/컨텍스트 크기를 제한한다. `SafetyGate`는 백엔드가 반환한 검증·증거 승격 주장을 거부하거나 응답을 미검증으로 정규화한다.
- **회귀 평가에 데이터 분할과 오류 분석 장치가 있다.** 형식 라우팅 평가는 언어/그룹별 결과, 혼동 행렬, 오류를 산출하고 개발/홀드아웃 fixture의 중복을 검사한다. 단, 이 평가는 키워드 기반 설명 형식 선택에 국한된다.
- **문서가 검증의 한계를 숨기지 않는다.** T55는 통제 회귀 세트임을 밝히고 대규모 경험적 검증과 실시간 영속 저장 검증을 미완료로 구분한다. 이는 과장 방지에 도움이 된다.

## 주요 검토 의견

### 1. 제품 기준선과 실행 구현의 버전 경계가 불명확하다 — 높음

최상위 README는 기준선을 `v2.0+++`, 프로토콜은 활성 아키텍처 기준선을 `v2.0`으로 선언한다. 한편 `execution.py`는 자신을 v1.3 실행 경계의 최소 참조 하네스로 설명하고, 구현 범위도 입력된 인지 상태를 검증·포장하는 것으로 제한한다. 런타임 일부가 v2.0 아키텍처를 어느 수준까지 실행하는지, 참조 하네스와 새 런타임의 관계가 무엇인지 소비자가 한눈에 판단하기 어렵다.

**권고:** 하나의 지원 기준선 표를 두고 각 실행 경로/모듈의 프로토콜 버전, 실제 구현 범위, 미지원 동작을 명시한다. README의 `v2.0+++` 표기도 정식 버전 또는 개발 별칭으로 정의한다.

### 2. 문서의 PASS가 구현 동작을 입증하는 증거와 섞일 위험 — 높음

T54/T55는 실제 출력 표면과 여러 문서 유형에 대한 결과를 PASS로 적지만, fixture/통제 회귀 집합 기반이다. 문서 자체가 모집단 수준의 정확도, 자동 문장별 저자 판별, 라이브 Notion 저장을 입증하지 않는다고 밝힌다. 따라서 PASS를 제품 전반의 정확성이나 운영 준비 완료로 해석하면 안 된다. `T55` 다음 단계도 전체 파이프라인 회귀(T56)로 제안돼 있다.

**권고:** 검증 기록마다 `명세 검토 / fixture 회귀 / 실제 생성 / 외부 시스템 통합` 중 증거 수준을 표준 필드로 기록하고, PASS 범위를 제목과 요약에 노출한다. T56 또는 동등한 end-to-end 실행 아티팩트가 나오기 전에는 통합 완료로 표기하지 않는다.

### 3. 배포·설치 진입점과 의존성 계약이 저장소 최상위에서 보이지 않는다 — 중간

검토한 최상위 파일 목록에는 `pyproject.toml`, `setup.cfg`, `requirements.txt` 같은 일반적인 Python 설치/의존성 정의가 보이지 않았다. 평가 스크립트의 실행 안내는 `PYTHONPATH=src/co_thoughts`를 요구하고, 모듈은 `from execution import ...`와 같은 최상위 모듈 import를 사용한다. 명시적인 로컬 실행은 가능해도, 표준 패키지 설치 및 외부 소비 방식이 분명하지 않다.

**권고:** 지원 설치/실행 방식을 정하고 메타데이터, 의존성, 공개 API/진입점을 문서화한다. 패키징을 의도하지 않는 참조 구현이라면 그 점과 검증된 실행 명령을 명확히 한다.

### 4. 이 정적 검토에서는 테스트 결과를 재현하지 않았다 — 중간

테스트 파일과 평가 데이터는 확인했으나 실행하지 않았다. 따라서 이 리뷰는 회귀 테스트 통과, 환경 재현성, 런타임/외부 연동 성공을 보증하지 않는다. 특히 문서 기반 PASS와 실행된 테스트 결과를 별도 기록으로 관리할 필요가 있다.

**권고:** 병합 또는 릴리스 게이트에 깨끗한 환경에서의 설치 및 단위/통합/평가 스위트 실행 결과를 연결한다. 외부 제공자 연동은 모의 테스트와 실제 연동 검증을 구분한다.

## 범위와 신뢰 경계

- 검토한 핵심 구현은 backend 앞뒤의 검증 및 상태 경계를 제공하지만, 그 자체가 진실 판정이나 일반 목적의 추론 품질을 증명하지 않는다.
- 외부 도구 실행과 부작용은 기본 비활성화되어 있어 안전한 기본값이다. 운영자가 활성화하는 경우 capability 등록, 페이로드/출력 제한, 권한 부여 경로를 배포 설정에서 별도 검증해야 한다.
- 저장소 라이선스는 CC BY-NC 4.0으로 명시돼 있다. 상업적 사용 계획이 있다면 별도 권한이 필요하다.
- 중첩 저장소의 Git 상태 확인은 실행 환경의 `dubious ownership` 보호로 차단되어, 기존 변경 여부를 이 검토에서 확정하지 못했다.

## 권고 우선순위

1. 기준선/지원 범위/구현 상태 표준화.
2. 문서 기반 PASS와 실행 증거의 표준 구분, 전체 파이프라인 테스트 결과 연결.
3. 설치 및 재현 절차 명문화(패키징 여부 포함).
4. 가능하면 실제 외부 저장 연동의 쓰기 후 읽기 검증을 별도 역량 경계와 함께 기록.

## 결론

이 저장소는 인식론적 안전 원칙을 코드 경계로 옮기려는 방향이 강하고, 기본 거부와 상태 분리 설계도 타당하다. 다만 현재 근거는 아키텍처/명세와 제한된 회귀 fixture에 치우쳐 있다. 버전 경계와 실제 구현 수준을 분명히 하고 재현 가능한 end-to-end 증거를 추가하기 전까지는 **연구/프로토타입 단계의 참조 구현**으로 평가하는 것이 적절하다.

## 부록 — GitHub PR #20 반영 여부 및 평가

앞선 초안에는 **PR #20의 diff가 반영되지 않았다.** 이 부록에서 GitHub의 [PR #20](https://github.com/ydonchoi/co-thoughts/pull/20)을 별도로 확인해 반영한다.

PR #20은 `test: independent evaluation set for format routing (guidelines + annotator A)`라는 제목이지만, 실제 병합 diff는 독립 평가 지침의 한국어·영어 파일 및 testing README 색인 추가다. 설명도 Annotator A 산출물을 후속으로 추가한다고 하고, 독립 데이터셋과 라벨은 이후 절차로 남긴다. 따라서 병합된 변경 자체는 **평가 세트를 포함하지 않고, 평가 세트를 만들기 위한 프로토콜**을 추가한 것이다. PR 대화에는 Codex 평가자 A를 요청하는 댓글이 있지만, 그 댓글만으로 세 산출 파일이 PR diff에 병합됐다고 볼 수 없다.

### PR #20의 기여

- 기존 라우팅 평가 데이터와 라벨을 규칙 작성자가 직접 만들었다는 독립성 문제를 명시한다.
- 80개(영어 40, 한국어 40) 과제의 그룹 구성, 일곱 라벨 정의, 출력 요청과 주제 언급 구분, 애매한 사례 처리 방식을 사전 규정한다.
- 과제·평가자 A 라벨·출처 기록을 분리하고, 라우터를 실행하기 전 파일을 고정하도록 해 누출 위험을 줄이려 한다.
- 평가자 B, Cohen's kappa, 사람 판정 표본, 라우터 점수 산출은 후속으로 분리한다. 따라서 독립성 보강의 설계는 있으나, 신뢰도나 라우터 성능 결과는 아직 이 PR이 제공하지 않는다.

### 검토 의견

**평가: 좋은 평가 프로토콜 개선. 측정 결과나 독립 벤치마크가 완성된 것으로 보기는 이르다.** 지침은 중요한 편향을 솔직하게 드러내고 작업을 재현 가능한 단계로 나눈 점이 좋다. 다만 PR 본문은 “guidelines + annotator A”라고 표현하는 반면, 병합 diff에서 확인되는 변경은 지침 파일뿐이고 본문도 Annotator A는 요청 시 추가한다고 한다. 제목/요약은 실제 포함 범위와 일치하게 다듬는 편이 정확하다.

완성 평가 세트로 인정하려면 최소한 `tasks.json`, `labels_annotator_a.json`, `PROVENANCE.md`가 실제로 추가되고, 각 80개 ID와 언어/그룹 수가 지침을 만족하는지 확인해야 한다. 이후 평가자 B의 독립 라벨, 일치도 및 판정 절차를 별도 증거로 제시하고, 라우터 실행 결과는 평가자 A/B/사람 판정 기준을 분리해 보고해야 한다. 사람 판정 20–30건만으로 전체 데이터셋을 “사람 검증 벤치마크”라고 부르지 않는다는 PR의 제한도 유지해야 한다.

**판정 보정:** 저장소 전반 리뷰의 “독립적·경험적 검증이 제한적”이라는 결론은 PR #20으로 수정되지 않는다. PR #20은 그 격차를 메우는 지침을 추가하지만, 검증 데이터와 성능 결과 자체를 추가하지는 않는다.
